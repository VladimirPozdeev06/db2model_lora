# EXPERIMENTS — ветка db2model (SFT/LoRA)

Журнал прогонов. Каждая запись — что запускали, на чём, что получилось.
Числа без указания выборки и модели бессмысленны, поэтому они здесь всегда рядом.

Целевые базы (согласованы с веткой RAG, чтобы сравнение было честным):
`financial`, `toxicology`, `codebase_community`.

Замеры снимаются на `bird_large` (241 вопрос, 91 по нашим трём базам).
`bird_small` — 22 вопроса и целиком входит в `bird_large`, годится только для отладки.

## 2026-07-16 — baseline стенда

Qwen2.5-Coder-7B (эндпоинт МФТИ), схема в промпте, `bird_small`, весь стенд как есть.

| метрика | значение |
|---|---|
| EX | **22.73%** (5/22) |
| prompt-токенов на вопрос | ~2 535 |
| completion-токенов на вопрос | ~146 |

По сложности: simple 22.2%, moderate 10.0%, challenging 66.7% (на 3 вопросах — шум).

**Число не является честной точкой отсчёта.** 9 из 22 вопросов провалил стенд, а не модель:

- ambiguity-check объявил неоднозначными 4 нормальных вопроса (18.2%) → гарантированный ноль;
- `sanitize_sql()` сломал валидный SQL на 5 вопросах (qid 13, 589, 685, 1365, 1472):
  регулярка «DISTINCT + ORDER BY → подзапрос» выносит ORDER BY наружу, колонка остаётся внутри;
- gold SQL портился самим стендом (qid 1533) — исправлено, см. ниже.

2 535 prompt-токенов при схеме в ~400 — потому что на вопрос идёт ambiguity-check плюс до
`MAX_RETRIES=7` генераций, и схема летит в каждый вызов.

## 2026-07-17 — первый сквозной прогон QLoRA

Qwen2.5-Coder-3B-Instruct, 4-bit, T4 (15.6 ГБ), toxicology, 16 пар (13 train / 3 val), 3 эпохи.

| метрика | значение |
|---|---|
| память после загрузки | 9.67 ГБ |
| пик при обучении | 10.92 ГБ |
| адаптер | 71.4 МБ |
| **EX (без схемы, 35 вопросов toxicology)** | **0.00%** |

Из 35 предсказаний: 20 — несуществующая таблица, 15 — несуществующая колонка, исполнимых ноль.

**Это не провал метода, а отсутствие данных**: 13 примеров × 3 эпохи ≈ 4 шага оптимизатора.
Ценность прогона в том, что петля замкнулась целиком: БД → профиль → учитель → фильтр → Kaggle →
предсказания → EX дома через туннель.

Проверенная и **отклонённая** гипотеза: «модель принимает db_id за схему». Префикс `toxicology.`
стоял в 13 из 35 запросов, но его снятие даёт те же 0/35 — там и колонки выдуманы.

Сравнивать этот 0% с 22.73% нельзя: другая модель, другая выборка, другой промпт.

## 2026-07-17 — генерация синтетики, объём

`db2model/generate_pairs.py` + `filter_pairs.py`, учитель Qwen2.5-Coder-7B.

| БД | сырых | чистых | брак |
|---|---|---|---|
| toxicology | 192 | 134 | **30%** |
| financial | 200 | 136 | **32%** |
| codebase_community | 200 | 138 | **31%** |

**Брак 30–32% на трёх разных базах.** Разброс в 2 процентных пункта на 592 парах — это
устойчивое свойство учителя, а не особенность одной базы. Вот это число и есть «качество teacher»,
которое требует план.

Структура брака (toxicology, n=58): `UndefinedColumn` 19, `GroupingError` 12, пустой результат 10,
`SyntaxError` 9, не парсится 3, `DivisionByZero` 2, дубликат 2, `UndefinedTable` 1.

Что дало добавление компактной выжимки схемы и явного запрета префикса в промпт учителя:

- `UndefinedTable` — с доминирующей причины до **1** случая;
- префикс `toxicology.` — с 13 запросов до **0**;
- разнообразие по сложности — с 11/4/1 до 43/73/18.

Осталось `UndefinedColumn`, в основном `t1.molecule_id`/`t2.molecule_id` на таблице `connected`,
где такой колонки нет. Это предел учителя-7B; для того и нужен фильтр по исполнению.

### Датасет

`db2model/build_dataset.py` → `db2model/dataset/` (train 347 / val 61, сплит по каждой базе отдельно,
seed 0). Состав и хеши входов — в `manifest.json`, чтобы прогон можно было привязать к данным.

| | financial | toxicology | codebase_community |
|---|---|---|---|
| пар | 136 | 134 | 138 |

По сложности суммарно: simple 148, moderate 218, challenging 42.

Отдельная находка: базы **недо-объявляют FK**. У toxicology объявлено 3, а связи
`atom.molecule_id → molecule.molecule_id` среди них нет. Правило «соединяй только по объявленным FK»
запрещало бы легальный JOIN, поэтому в промпт достраиваются неявные связи по совпадению имени
с первичным ключом (`_implied_edges`): toxicology +2, codebase_community +7, financial +0.

## 2026-07-17 — ГЛАВНЫЙ ЗАМЕР: знание в контексте против знания в весах

Первое честное сравнение. Один прогон, **одна модель** (Qwen2.5-Coder-3B-Instruct, 4-bit),
**одни вопросы** (91 из `bird_large` по трём базам), один код генерации. Отличается ровно то,
что проверяем: схема в промпте против адаптера. Обучение — 347 пар синтетики, 3 эпохи, LoRA r=16.

| Арм | схема в промпте | адаптер | **EX** | prompt-токенов |
|---|---|---|---|---|
| `baseline` | да | выключен | **23.08%** (21/91) | 288 |
| `lora` | нет | включён | **19.78%** (18/91) | 91 |

По сложности:

| | simple | moderate | challenging |
|---|---|---|---|
| baseline | 28.57% | 24.24% | 13.04% |
| lora | 31.43% | 9.09% | 17.39% |

**Что это значит.** LoRA отстаёт на 3.3 процентных пункта при контексте в 3.2 раза меньше.
Для 3B, которая схему в глаза не видела и достаёт её из весов, это неожиданно близко.
На простых вопросах она даже обходит baseline (31.4% против 28.6%), проваливаясь на moderate
(9.1% против 24.2%) — похоже, 347 примеров хватает на типовые запросы и не хватает на составные.

**Экономия токенов реальна, но ничего не стоит.** 288 → 91 это минус 68% контекста, то есть
около 200 токенов на запрос у локальной 3B. Это не деньги. Против — часы GPU на обучение.
Продавать ветку как «экономию контекста» нельзя, см. замер размеров схем выше.

### Найденный при этом баг оценки (важно для честности)

Первый подсчёт дал baseline 21.98% против lora 19.78%. Разница оказалась частично артефактом
**моего** кода: `clean_sql` снимал ограждения ` ``` ` только по краям строки, а модель без
дообучения охотно пишет «To find X, use:» и потом блок кода — вся проза уезжала в базу как SQL
и получала ноль. Таких ответов у `baseline` **9 из 91**, у `lora` — **0** (дообученная модель
выдаёт голый SQL). То есть наивный парсер штрафовал ровно тот арм, с которым сравниваемся.

Написан `db2model/extract_sql.py` (блок кода → первый `SELECT`/`WITH` → обрезка). Пересчёт:
baseline 21.98% → **23.08%**, lora 19.78% → **19.78%** (переписано 0 из 91).

Баг стоил одного вопроса, а не девяти — проза и так была в основном неверной. Но проверять было
обязательно: иначе в отчёт ушло бы число, льстящее собственной ветке из-за собственной ошибки.
В ноутбуке `clean_sql` исправлен.

## Открытые вопросы

- **Teacher = Qwen2.5-Coder-7B, а не GPT-4-class.** На эндпоинте одна модель, проверено через
  `/v1/models`. Дистилляция «сильный → слабый» вырождается. Вопрос куратору не закрыт.
- **Почему lora проваливает moderate** (9.1% против 24.2% у baseline), обходя baseline на simple —
  главная зацепка для недели 5. Гипотеза: 347 примеров хватает на типовые запросы, не хватает на
  составные. Проверяется кривой «размер синтетики → EX».
- **Tool-calling на эндпоинте выключен** (`--enable-auto-tool-choice` не задан) — агентный baseline
  стенда на нём не заведётся. Ветке db2model не мешает, куратору сказать стоит.
- **`train_queries.json` (357 реальных пар, 143 по нашим базам) не задействован.** Это буквально
  обучающий набор из ROUTE и естественная верхняя оценка качества синтетики.
- **ROUTE читается не так, как записано в плане**: там не учитель генерирует пары, а берутся
  реальные SPIDER+BIRD и из них синтезируются 4 формата задач (TS/SL/NC/CW). MSFT в план не заложен.
