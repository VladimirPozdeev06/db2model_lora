# Финальная сравнительная таблица — DB2Model (обе ветки)

Сводит результаты **обеих веток практики** на одном split, чтобы сравнить два способа
«переложить знание о БД» из плана куратора:

- **Distillation A — light-RAG** (граф знаний, ветка напарницы) — обязательная основная;
- **Distillation B — SFT/LoRA** (знание в весах, наша ветка) — «растяжимая».

**Общий split (для всех армов обеих веток):** 91 вопрос `bird_large` по трём базам —
`financial` 29 + `toxicology` 35 + `codebase_community` 27. Один исполнитель SQL, один
парсер результата, один оценщик (`benchmarks/evaluate_bird.py`, EX/VES).

## Что показывает таблица

По главной оси задачи («сколько токенов на запрос при каком EX/VES относительно baseline»)
две ветки ведут себя качественно по-разному:

- **light-RAG улучшает точность, но тратит больше токенов.** V3: EX 24.18 → 28.57 (+4.4 п.п.),
  но токены растут (+46% end-to-end). В компактном режиме (V4) токены схемы падают на 84%,
  но EX проваливается до 19.78. Ветка сидит на компромиссной кривой «точность ↔ токены».
- **SFT/LoRA выигрывает на обеих осях сразу.** 7B: EX 41.03 при ~90 ток. — и точнее, и
  короче по контексту. Экономия токенов не в ущерб точности, а вместе с ней.

**Вывод для защиты:** для per-DB сценария знание в весах (SFT) доминирует над знанием в
контексте и над графовым извлечением по совокупности EX × токены; light-RAG остаётся
сильным, когда дообучение под каждую БД невозможно (новая база без переобучения).

## ⚠️ Оговорка по токенам (проверено по коду обеих веток)

**Одинаково ли мы меряем токены? — Нет, не полностью.** Три расхождения:

1. **Низкоуровневый счётчик — общий.** `benchmarks/token_tracking.py` в обоих репозиториях
   практически идентичен: берёт `usage.prompt_tokens` из ответа сервера модели (реальный
   токенайзер Qwen). На этом уровне метод один.

2. **Размеры схем считаются чужим токенайзером.** И у нас (`collect_profile.py`), и у неё
   (в `research_log.md` — «cl100k tokens») размер схемы/профиля меряется через
   `tiktoken cl100k_base` — это токенайзер OpenAI, а модель — Qwen. Он консистентен
   _между ветками_, но не равен реальному числу токенов модели.

3. **Разный охват (главное расхождение).** Наши `~90 / ~288` — это **один вызов** target
   с **лёгкой** схемой (таблицы/колонки/типы). Её `~2307 / ~2664 / ~3368` — **полная тяжёлая**
   схема (+ описания + примеры строк + evidence) и/или **end-to-end** с вызовом ретривера,
   возможно + отдельный ambiguity-вызов. Поэтому «288 vs 2307» для номинально одного и того
   же «7B baseline со схемой» — это разница конфигурации и охвата, а не модели.

4. **Наша половина закрыта точным замером (обновлено).** `measure_tokens.py` строит промпт
   каждого арма ровно как `kaggle_infer_7b.ipynb` (тот же `build_prompt` / `schema_text`) и
   считает токенайзером Qwen2.5-Coder через `apply_chat_template(add_generation_prompt=True)`.
   Результат (`results/token_budget.json`, 91 вопрос): **schema-less 90.6 ± 34.8**
   (медиана 79, 49–206), **baseline 288.2 ± 117.3** (медиана 316, 109–492). Отношение
   288.2 / 90.6 = **×3.18** — подтверждает «×3.2 меньше контекст». По базам виден эффект
   размера схемы у baseline: toxicology 152.9 → financial 330.6 → codebase_community 418.1;
   у schema-less такого нет (схемы в промпте нет), его разброс — только от длины вопроса.

**Осталось для честной колонки по light-RAG:** напарнице снять токены **тем же определением** —
prompt-токены генерационного вызова, токенайзером Qwen через `apply_chat_template`. Проще всего:
дамп финального промпта на каждый вопрос → прогнать через наш `measure_tokens.py` (подставив её
builder), либо `usage.prompt_tokens` генерационного вызова с её сервера. Тогда «~» уходит и у неё.

## Открытые пункты сведения

- Baseline'ы веток **не идентичны**: её — 7B + полная схема (2307 ток., EX 24.18, режет
  ambiguity-check); наш — лёгкая схема (288 ток., 3B → 24.18 / 7B → 30.77). Для «единой точки
  отсчёта» (требование DoD) нужно договориться об одном baseline-агенте.
- Совпадение EX **24.18%** у её 7B-baseline и нашего 3B-baseline (оба = 22/91) — вероятно,
  общий потолок из неисполнимого gold (BIRD SQLite→Postgres через sqlglot: непро­исполнившийся
  gold засчитывается провалом всем армам). Стоит посчитать долю мёртвого gold — она калибрует
  все числа обеих веток.
- Строка light-RAG в `leaderboard.md` всё ещё `_TBD_` — сюда сведены её реальные числа (V3),
  осталось подтвердить на общем синке.
