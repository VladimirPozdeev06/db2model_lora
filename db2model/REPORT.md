# DB2Model — ветка SFT/LoRA: технический отчёт (черновик)

> Отчёт по «растяжимой» ветке distillation-B (SFT/LoRA) практики DB2Model.
> Обязательная главная ветка (light-RAG) — у напарницы; сюда сводится в финале.
> Числа с пометкой _TBD_ снимаются последним прогоном (VES) и на общем синке (RAG).

## 1. Постановка

Задача DB2Model: переложить знание о конкретной PostgreSQL-БД в модель, чтобы
Text2SQL-инференс не тратил контекст на повторную «выкачку» схемы. Ветка SFT/LoRA
проверяет гипотезу «знание в весах»: teacher-модель по профилю БД генерирует пары
«вопрос → SQL», их фильтруют исполнением на живой базе, на очищенных парах обучается
компактная target-модель (QLoRA). На инференсе схема в промпт не подаётся.

Baseline — та же target-модель со схемой в промпте (знание в контексте).
Целевые базы: `financial`, `toxicology`, `codebase_community` (согласованы с веткой RAG).
Метрики: **EX**, **VES**, **prompt-токены/запрос**. Split: 91 вопрос `bird_large`.
Target: Qwen2.5-Coder-3B-Instruct (4-bit).

## 2. Pipeline

```
профиль БД → генерация пар teacher → фильтр исполнением → датасет → QLoRA (Kaggle) → предсказания → EX/VES (дома)
collect_profile  generate_pairs        filter_pairs       build_dataset  kaggle_*.ipynb            bird_evaluate_only
```

Всё, кроме обучения, — локально (нужен ssh-туннель к БД). Обучение — на Kaggle
(база из Kaggle не видна): туда датасет, оттуда предсказания и адаптер, EX/VES дома.
Профиль БД: схема + FK (+ неявные рёбра по совпадению имён с PK) + `pg_stats` +
реальные значения. Размеры профилей: financial 12k, toxicology 2.8k,
codebase_community 18.8k токенов.

Третий источник exploration из карточки — логи и планы — снимается отдельно
(`collect_query_stats.py` → `profiles/<db>.plans.json`): счётчики обращений к таблицам из
`pg_stat_user_tables`, планы `EXPLAIN (FORMAT JSON)` по 234 реальным запросам (143 пары
`train_queries.json` + 91 gold оценочного split) и join-пути с ключами. Настоящий лог
запросов (`pg_stat_statements`) на инстанции недоступен: расширение не установлено, прав
суперюзера и `pg_read_all_stats` у нас нет. В обучение адаптера эти артефакты не заведены —
победитель обучен без них; применение (взвешивание синтетики по реальным join-путям)
остаётся заделом.

## 3. Результаты

### Ранний замер (train 1171, учитель Qwen-7B) — исторический

Блок ниже сохранён как история: на нём отрабатывались сиды, аудит утечки и кривая объёма
данных. Актуальные числа ветки — в следующем подразделе.

| Арм | Схема | EX | prompt-ток. |
|---|---|---|---|
| zeroshot (контроль) | нет | 5.49% | 90 |
| baseline (детерминирован) | в контексте | 23.08% | 288 |
| **lora** (среднее 3 сидов) | в весах | **27.84% ± 0.52** | 90 |

lora по сидам 0/1/2: 27.47 / 27.47 / 28.57%; одиночный seed 42 давал 29.67% (выше среднего).

**Знание в весах обгоняет знание в контексте: lora 27.84% ± 0.52 vs baseline 23.08% = +4.8 п.п.**
(≫ σ), при контексте в 3.2 раза меньше. Контроль `zeroshot` (та же 3B без схемы и без адаптера) даёт
5.49% — значит адаптер переносит в веса **+22 п.п.** знания о схеме, это не артефакт базовой
модели. VES ≈ EX во всех армах (тайминг через ssh шумит, отдельного сигнала нет).

Результат обеспечен **объёмом синтетики**. Кривая по размеру train: 9.9 (50) → 11.0 (143) →
16.85 (347) → **27.84 (1171, 3 сида)**, плато нет. На 347 парах lora ещё проигрывала baseline ~3 п.п.;
масштаб ×3.4 (учитель + фильтр исполнением) перевернул знак. baseline детерминирован (greedy),
lora усреднена по 3 сидам (σ = 0.64 п.п.); разрыв кратно больше σ.

### Обновление: сильный учитель + канонический оценщик

Числа выше — на **нашем** оценщике (учитель Qwen2.5-Coder-7B, 1171 sql-пар). Затем
учитель заменён на **Qwen3.6-27B** (сильный open-teacher из пула МФТИ), датасет
перегенерён (1290 чистых пар, брак 9–19% против 30–37% у 7B), а все армы прогнаны
через **единый оценщик напарницы** (`evaluate_bird.py` + `bird_large_filtered.json`)
для сравнимости веток.

Числа ниже — **пересчёт 10.08.2026**, воспроизводимый из репозитория (см. подраздел
о расхождении с июльскими значениями).

| Арм (lora = знание в весах) | Учитель / данные | EX | prompt-ток. |
|---|---|---|---|
| zeroshot (контроль) | — | 5.49% | 90 |
| baseline **3B** | схема в контексте | 24.18% | 288 |
| new_lora **3B** | Qwen-27B, 2699, +мультизадачи (1 сид) | 28.57% | 90 |
| qwen27b_sql_only **3B** | Qwen-27B, 1096, sql-only (3 сида) | 30.77% ± 1.55 | 90 |
| baseline **7B** | схема в контексте, target 7B | 30.77% | 288 |
| reasoning **7B** | Qwen-27B, 1096 CoT (1 сид) | 30.77% | 90 |
| **qwen27b_sql_only 7B** | **Qwen-27B, 1096, sql-only (3 сида)** | **41.03% ± 1.37** | **90** |

**Итог: лучшее число — target 7B (плановая основная модель), `qwen27b_sql_only` =
41.03% ± 1.37 (сиды 40.66/42.86/39.56), знание в весах +10.3 п.п. над 7B-baseline (30.77)**
при контексте в 3.2× меньше и генерации в 1.44× быстрее; разрыв ≈ 7.5 σ. Тезис держится и
на 3B: 30.77% ± 1.55 (сиды 31.87/28.57/31.87) против baseline 24.18% = **+6.6 п.п.** (≈ 4 σ).

> Прежняя формулировка «+9.5 п.п. на обоих размерах» **снята**: она держалась на июльском
> замере и оказалась совпадением. Прирост есть на обоих размерах, но он разный — 3B выигрывает
> заметно скромнее, потому что при пересчёте baseline 3B подрос сильнее, чем lora.

Ablation (с поправкой на сид):
- **Reasoning (Think2SQL) вредит:** 30.77 против 41.03 ± 1.37 = −10.3 п.п., ≈ 7.5 σ —
  **единственный ablation ветки с доказанным знаком** (разбор ниже).
- **Мультизадачность ROUTE — не доказана:** new_lora 28.57 (1 сид) совпадает с нижним сидом
  победителя (диапазон 28.57–31.87) и лежит внутри ±σ. На июльском замере она была ниже всего
  диапазона — отсюда прежний вывод «вредит»; после пересчёта он **не подтверждается**.
  Мультизадачи остаются выключенными как выбор по умолчанию, а не как доказанный вред.
- **Учитель 7B→27B:** old_lora 27.47 (1 сид, июльский замер) внутри ±σ победителя — эффект
  учителя **в пределах шума**; данные при этом объективно чище (брак 9–19% против 30–37%).

### Расхождение с июльскими числами

Июльские канонические значения (38.09 / 29.30 / 28.57 / 19.78 / 25.27 / 4.40) **не
воспроизводятся**: на тех же файлах предсказаний и том же gold каждый арм даёт на 1–4
вопроса больше (zeroshot +1, baseline 3B +4, sql-only 3B +1/+1/+2, new_lora +3,
baseline 7B +2, sql-only 7B +2/+3/+3). Сдвиг односторонний у всех армов без исключения,
то есть это свойство стенда, а не моделей: `evaluate_bird.py`, `uv.lock` и
`sqlite_to_postgres` с июля не менялись (проверено по git). Правдоподобное объяснение —
июльские числа снимались в другом окружении, с другими версиями библиотек: gold BIRD
транспилируется из SQLite в PostgreSQL через sqlglot, и gold, который не исполнился,
засчитывается провалом всем армам сразу. Строго причина не установлена. Канон — пересчёт,
как единственные воспроизводимые числа.

Победивший адаптер — `adapters/qwen27b_sqlonly1096/`; предсказания —
`results/query_results_qwen27b_sqlonly_seed{0,1,2}.json`.

### Ablation: reasoning-трейсы (Think2SQL) — отклонено

Проверена вторая техника из опорных статей: учить target не только SQL, но и цепочке рассуждений
(1096 CoT-пар от Qwen-27B, `kaggle_train_reasoning.ipynb`, target 7B, 1 сид).

| Арм (target 7B) | EX | VES | simple / moderate / challenging |
|---|---|---|---|
| baseline (схема в контексте) | 30.77% | 30.55 | 45.7 / 21.2 / 21.7 |
| **reasoning (CoT)** | **30.77%** | 29.51 | 48.6 / 21.2 / 17.4 |
| **sql-only (3 сида)** | **41.03% ± 1.37** | 41.01 | 64.8 / 32.3 / 17.4 |

**Reasoning −10.3 п.п. против sql-only** (≈ 7.5 σ) и **ровно сравнялся с baseline** — CoT-обучение
съело всё преимущество «знания в весах». Механизм: модель разучилась помнить схему — 34 запроса
из 91 ссылаются на несуществующие колонки против 16 у sql-only (сверка sqlglot с `profiles/`),
и просели именно **simple** (48.6 против 64.8), то есть запросы на припоминание имён; challenging
у обоих упёрся в общий потолок 17.4%. Ёмкость LoRA ушла на трейсы вместо схемы.

Это **единственный ablation ветки с доказанным знаком** — мультизадачность, эффект учителя и
эффект фильтра после пересчёта остались в пределах шума, а reasoning проваливается на 7.5 σ.
Вывод для защиты: ёмкость LoRA конечна, и потраченная на рассуждения — это ёмкость, не
потраченная на схему. Для per-DB SFT оптимум — чистый sql-only.

## 4. Что сработало и что нет

- **Знание в весах работает и обгоняет контекст** при достаточном объёме данных:
  на 1171 паре lora 27.84% ± 0.52 (3 сида) > baseline 23.08%. Ключ — количество синтетики: на 347
  парах lora ещё проигрывала, масштаб ×3.4 перевернул знак. Контроль zeroshot (5.49%) доказывает,
  что +22 п.п. над ним — заслуга адаптера, а не базовой модели.
- **Фильтр по исполнению** осмыслен (брак teacher 30–37%): учит на исполнимом SQL. Его
  изолированный вклад на малых наборах был в пределах шума — но именно фильтрованная
  синтетика в объёме дала итоговый результат.
- **Экономия токенов** реальна (90 vs 288), и теперь она бесплатна не в ущерб точности:
  lora и точнее, и втрое компактнее по контексту. На больших схемах (которые в промпт
  не влезают) это и есть главный смысл ветки.

## 5. Ограничения

- **Teacher = Qwen3.6-27B, не GPT-4-class.** Внешний API под разметку не выдали, 27B — потолок
  в рамках ограничений (ранние замеры — на Qwen2.5-Coder-7B). Классическая дистилляция
  «сильный → слабый» вырождается; честная формулировка вклада — перенос схемы в веса
  + noise correction через исполнение. Эффект самого апгрейда учителя строго не доказан:
  old_lora (1 сид) попадает внутрь ±σ победителя, зато данные объективно чище (брак фильтра
  9–19% против 30–37%).
- **Per-DB / multi-DB.** Обучен один адаптер сразу на три базы; обобщение на новую БД
  без дообучения — вне скоупа.
- **Шум прогонов и сиды.** Главный замер (train 1171) усреднён по 3 сидам (0/1/2): EX
  27.47/27.47/28.57 → **27.84% ± 0.52**. baseline детерминирован (greedy). Разрыв +4.8 п.п. кратно
  больше σ — знак надёжен. Одиночный seed 42 давал 29.67% (выше среднего) — иллюстрация, зачем нужны
  повторы. ablation-варианты (фильтр, real vs synth) всё ещё по одному сиду.
- **Утечка train→eval.** `check_leakage.py` нашёл 2 оценочных вопроса (q320, q323, toxicology) с
  точным gold-SQL-твином в обучении (генератор засеян реальными значениями БД). Без них разрыв
  даже растёт: lora 28.09 ± 1.12 vs baseline 22.47 (89 вопросов, 3 сида) = +5.6 п.п. Данные вычищены
  (`dataset/train_clean.json`, 1169), `build_dataset.py` деконтаминирует автоматически.
- **Диалект.** Gold BIRD (SQLite) приводится к PostgreSQL через sqlglot; редкие
  конструкции могут не транспилироваться.

## 6. План развития

Закрыто по ходу работы: target 7B прогнан (41.03 ± 1.37, лучшее число ветки), VES и латентность
сняты по всем армам, ablation по мультизадачам и reasoning доведены до чисел.

- **Больше синтетики** — кривая объёма не вышла на плато (9.9 → 11 → 16.85 → 27.84), это самый
  надёжный рычаг: единственный ablation-эффект, устойчивый за пределами σ.
- **Повторы ablation с сидами**: фильтр, real vs synth и old_lora гонялись по одному разу, их
  различия внутри шума — без повторов вклад учителя от вклада объёма не отделить.
- Сильный teacher (API GPT-класса) — проверить, добавляет ли реальная дистилляция.
- doc2lora (Text-to-LoRA) как альтернатива SFT: генерировать адаптер из описания БД.
- Свести с веткой light-RAG: EX/VES/токены на общем split → финальный выбор конфигурации.
- **Отдавать адаптер через vLLM**, чтобы schema-less арм давал верный SQL внутри MCP-процесса.

## 7. Артефакты

`collect_profile / build_mschema / generate_pairs / filter_pairs / build_dataset (с
деконтаминацией) / build_ablation / check_leakage`, Kaggle-ноутбуки (`kaggle_train_lora /
kaggle_train_7b / kaggle_ablation / kaggle_seeds`), `extract_sql`, оценщик с EX+VES; профили баз и
M-Schema (`mschema/<db>.txt`), датасеты (+ `manifest.json` с хешами, `train_clean.json`),
предсказания всех армов, адаптер (`adapters/synth1171/` + `adapter_card.json`),
`leaderboard.md`, `EXPERIMENTS.md` (журнал всех прогонов). MCP-сервер
(`src/adv_text2sql/mcp_servers/text2sql_tool/`) поддерживает арм весов через
`with_schema=False`; развёртывание — `MCP_SERVING.md`.

**Smoke-тест MCP (живой, воспроизводимый — `db2model/mcp_smoke_test.py`).** Прогнан
реальный путь `query()`: вопрос → LLM (эндпоинт МФТИ) → SQL → исполнение на живой БД
через туннель → таблица. В режиме `with_schema=True` — **3/3 PASS** по всем базам с
реальными числами: toxicology `SELECT DISTINCT bond_type FROM bond` → 3 строки;
financial `COUNT(*) FROM account` → 4500; codebase_community `COUNT(*) FROM users` → 40325.
**Schema-less арм в MCP — закрыт (10.08).** Адаптер отдан через vLLM с `--enable-lora`
(рецепт: `db2model/kaggle_vllm_serve.ipynb`), `.env` переставлен на этот эндпоинт, тест
ужесточён: теперь оба арма обязаны вернуть реальные строки по всем трём базам. Результат
на одном сервере, где рядом живут база и адаптер:

| Арм | модель | PASS |
|---|---|---|
| `with_schema=True` (схема в промпте) | базовая Qwen2.5-Coder-3B (`base`) | 2/3 |
| **`with_schema=False`** (знание в весах) | **адаптер (`db2model`)** | **3/3** |

Schema-less: `SELECT DISTINCT bond_type FROM bond LIMIT 3` → 3 строки, `COUNT(account_id)
FROM account` → 4500, `COUNT(*) FROM users` → 40325 — всё без единого упоминания схемы.
Baseline провалил `codebase_community`: базовая модель **со схемой в промпте** сослалась на
несуществующую колонку `userid`. Тезис ветки виден вживую, а не только в EX.

⚠️ **Промпт schema-less арма нельзя менять в отрыве от адаптера.** Адаптер обучен на
инструкции `You are a PostgreSQL expert for the database \`<db>\`. Return only SQL.`
и на голом вопросе в user-сообщении. Прежний русский промпт из 12 правил (с требованием
комментариев `/* */`) уводил его с обученного распределения: модель возвращала **только
комментарий**, MCP падал с «Incomplete SQL generated». Промпт приведён к обучающему,
предупреждение оставлено в `prompts.py`.
