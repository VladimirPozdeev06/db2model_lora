# DB2Model — ветка SFT/LoRA: технический отчёт (черновик)

> Отчёт по «растяжимой» ветке distillation-B (SFT/LoRA) практики DB2Model.
> Обязательная главная ветка (light-RAG) — у напарницы; сюда сводится в финале.
> Числа с пометкой _TBD_ снимаются последним прогоном (VES) и на общем синке (RAG).

## 1. Постановка

Задача DB2Model: переложить знание о конкретной PostgreSQL-БД в модель, чтобы
Text2SQL-инференс не тратил контекст на повторную «выкачку» схемы. Ветка SFT/LoRA
проверяет гипотезу «знание в весах»: teacher-модель по профилю БД генерирует пары
«вопрос → SQL», их фильтруют исполнением на живой базе, на очищенных парах обучается
компактная target-модель (QLoRA). На инференсе схема в промпт не подаётся.

Baseline — та же target-модель со схемой в промпте (знание в контексте).
Целевые базы: `financial`, `toxicology`, `codebase_community` (согласованы с веткой RAG).
Метрики: **EX**, **VES**, **prompt-токены/запрос**. Split: 91 вопрос `bird_large`.
Target: Qwen2.5-Coder-3B-Instruct (4-bit).

## 2. Pipeline

```
профиль БД → генерация пар teacher → фильтр исполнением → датасет → QLoRA (Kaggle) → предсказания → EX/VES (дома)
collect_profile  generate_pairs        filter_pairs       build_dataset  kaggle_*.ipynb            bird_evaluate_only
```

Всё, кроме обучения, — локально (нужен ssh-туннель к БД). Обучение — на Kaggle
(база из Kaggle не видна): туда датасет, оттуда предсказания и адаптер, EX/VES дома.
Профиль БД: схема + FK (+ неявные рёбра по совпадению имён с PK) + `pg_stats` +
реальные значения. Размеры профилей: financial 12k, toxicology 2.8k,
codebase_community 18.8k токенов.

## 3. Результаты

### Основной замер (train 1171)

| Арм | Схема | EX | VES | prompt-ток. |
|---|---|---|---|---|
| zeroshot (контроль) | нет | 5.49% | 5.35% | 90 |
| baseline | в контексте | 23.08% | 23.51% | 288 |
| **lora** | в весах | **29.67%** | **29.57%** | 90 |

**Знание в весах обгоняет знание в контексте: lora 29.67% vs baseline 23.08% = +6.6 п.п.**,
при контексте в 3.2 раза меньше. Контроль `zeroshot` (та же 3B без схемы и без адаптера) даёт
5.49% — значит адаптер переносит в веса **+24.2 п.п.** знания о схеме, это не артефакт базовой
модели. VES ≈ EX во всех армах: эффективность корректных запросов на уровне gold.

Результат обеспечен **объёмом синтетики**. Кривая по размеру train: 9.9 (50) → 11.0 (143) →
16.85 (347) → **29.67 (1171)**, плато нет. На 347 парах lora ещё проигрывала baseline ~3 п.п.;
масштаб ×3.4 (учитель + фильтр исполнением) перевернул знак. Числа с одного сида (baseline
детерминирован); разрывы кратно больше порога шума (< 3 п.п.), для строгого ± нужны повторы.

### Ablation по данным

| Вариант | EX | вывод |
|---|---|---|
| synth_50 / 143 / 347 | 9.9 / 11.0 / 16.85% | эффект размера ~8 п.п. — **устойчив** (>2σ) |
| synth_347 vs unfiltered_347 | 16.85 vs 15.4% | фильтр +1.5 п.п. — **внутри σ, не доказан** |
| real_143 vs synth_143 | 13.2 vs 11.0% | живые чище, но разница в пределах шума |

Устойчивый вывод один: **синтетики нужно больше** (кривая не вышла на плато).
Фильтр и «живые vs синтетика» — по одному сиду, различия внутри σ = 1.37.

## 4. Что сработало и что нет

- **Знание в весах работает и обгоняет контекст** при достаточном объёме данных:
  на 1171 паре lora 29.67% > baseline 23.08%. Ключ — количество синтетики: на 347 парах
  lora ещё проигрывала, масштаб ×3.4 перевернул знак. Контроль zeroshot (5.49%) доказывает,
  что +24 п.п. над ним — заслуга адаптера, а не базовой модели.
- **Фильтр по исполнению** осмыслен (брак teacher 30–37%): учит на исполнимом SQL. Его
  изолированный вклад на малых наборах был в пределах шума — но именно фильтрованная
  синтетика в объёме дала итоговый результат.
- **Экономия токенов** реальна (90 vs 288), и теперь она бесплатна не в ущерб точности:
  lora и точнее, и втрое компактнее по контексту. На больших схемах (которые в промпт
  не влезают) это и есть главный смысл ветки.

## 5. Ограничения

- **Teacher = Qwen2.5-Coder-7B, не GPT-4-class** (на эндпоинте одна модель). Дистилляция
  «сильный → слабый» вырождается; честная формулировка вклада — перенос схемы в веса
  + noise correction через исполнение, а не дистилляция.
- **Per-DB / multi-DB.** Обучен один адаптер сразу на три базы; обобщение на новую БД
  без дообучения — вне скоупа.
- **Шум прогонов.** σ = 1.37 п.п. на 91 вопросе; различия < 2–3 п.п. не обсуждаются.
  Главный замер усреднён по 3 сидам, ablation — по одному.
- **Диалект.** Gold BIRD (SQLite) приводится к PostgreSQL через sqlglot; редкие
  конструкции могут не транспилироваться.

## 6. План развития

- Больше синтетики (кривая растёт) и повторы ablation с сидами для доказательности.
- Сильный teacher (API GPT-класса) — проверить, добавляет ли реальная дистилляция.
- doc2lora (Text-to-LoRA) как альтернатива SFT: генерировать адаптер из описания БД.
- Свести с веткой light-RAG: EX/VES/токены на общем split → выбор конфигурации → MCP.
- Снять VES по всем армам (оценщик готов) и латентность — для многокритериального выбора.
