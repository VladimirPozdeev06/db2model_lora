# DB2Model — знание о БД в весах, а не в контексте

Ветка SFT/LoRA летней практики. Идея: teacher-модель по профилю конкретной PostgreSQL-БД
генерирует пары «вопрос → SQL», их фильтруют исполнением на живой базе, на очищенных парах
дообучается небольшая target-модель через QLoRA. Знание о базе оказывается в весах, поэтому
на инференсе схема в промпт не подаётся — на вход идёт только вопрос.

Сравнивается с baseline: та же target-модель со схемой в промпте (знание в контексте).

## Результаты

Всё на 91 вопросе из `bird_large` по трём базам (`financial`, `toxicology`, `codebase_community`),
target — Qwen2.5-Coder-3B-Instruct в 4-bit. Подробности и оговорки — в [../EXPERIMENTS.md](../EXPERIMENTS.md).

### Главный результат

Победитель — **`qwen27b_sql_only`**: учитель Qwen3.6-27B, 1096 sql-пар, без мультизадач.
Все армы — через **единый оценщик напарницы** (`evaluate_bird.py` + `bird_large_filtered.json`),
чтобы числа были сравнимы между ветками SFT и light-RAG.

| Арм (lora = знание в весах) | target | Схема в промпте | EX | prompt-токенов |
|---|---|---|---|---|
| baseline напарницы (light-RAG) | — | — | 24.18% | — |
| baseline | 3B | да | 19.78% | 288 |
| baseline | 7B | да | 28.57% | 288 |
| qwen27b_sql_only (3 сида) | 3B | нет | 29.30% ± 1.37 | 90 |
| **qwen27b_sql_only** (3 сида) | **7B** | нет | **38.09% ± 1.37** | **90** |

**Знание в весах обгоняет знание в контексте — на обоих размерах модели, оба сид-подтверждены:**
- **7B** (плановая основная): lora **38.09% ± 1.37** (сиды 38.46/39.56/36.26) vs baseline 28.57% = **+9.5 п.п.** при контексте в 3.2× меньше. Лучшее число, выше baseline напарницы (24.18) на +13.9.
- **3B**: lora 29.30% ± 1.37 (сиды 30.77/27.47/29.67) vs baseline 19.78% = **+9.5 п.п.**

Оба разрыва кратно больше σ = 1.37. Адаптеры — `adapters/qwen27b_7b_sqlonly1096/` (7B) и
`qwen27b_sqlonly1096/` (3B); данные — `kaggle_input/` (sql_only; мультизадачи дали −4 п.п.
и отключены, воспроизводятся флагом `build_dataset.py --multitask`).

### Ранний замер (наш оценщик, train 1171)

Числа ниже сняты **нашим** оценщиком на прежнем учителе (Qwen-7B) — исторический контекст,
на нём отрабатывались сиды, утечка и ablation по объёму. Итоговое число для защиты — 32.97% выше.

| Арм | Схема в промпте | EX | prompt-токенов |
|---|---|---|---|
| zeroshot (контроль) | нет | 5.49% | 90 |
| baseline (детерминирован) | да | 23.08% | 288 |
| **lora** (3 сида) | нет | **27.84% ± 0.64** | 90 |

lora по сидам 0/1/2: **27.47 / 27.47 / 28.57%**; ранее публиковавшийся одиночный прогон (seed 42)
дал 29.67% — **выше среднего**, т.е. один сид был оптимистичен. По честному среднему трёх сидов:

**Знание в весах обгоняет знание в контексте: lora 27.84% ± 0.64 vs baseline 23.08% = +4.8 п.п.**
(разрыв ≫ σ), при контексте в 3.2 раза меньше (90 vs 288 токенов). Что это заслуга адаптера, а не
базовой модели, доказывает контроль `zeroshot` (та же 3B без схемы и без адаптера) — 5.49%: обучение
переносит в веса **+22 п.п.** знания о схеме. `VES ≈ EX` во всех армах (тайминг через ssh шумит,
отдельного сигнала не даёт).

Ключ к результату — **объём синтетики**. По размеру train: 9.9 (50) → 11.0 (143) → 16.85 (347) →
**27.84 (1171, 3 сида)**. На 347 парах lora ещё проигрывала baseline ~3 п.п.; масштаб ×3.4 (учитель +
фильтр исполнением) перевернул знак. Кривая не вышла на плато. baseline детерминирован (greedy);
lora усреднена по сидам 0/1/2, σ = 0.64 п.п. — разрыв с baseline кратно больше σ.

**Проверка на утечку train→eval.** Генератор засеян реальными значениями из БД, поэтому мог
сгенерить обучающую пару с тем же gold-SQL и теми же литералами, что оценочный вопрос. Скрипт
`check_leakage.py` (точное совпадение нормализованного gold-SQL с сохранением литералов) находит
**2 таких вопроса — q320 и q323** (оба toxicology). После их исключения из оценки картина не меняется:

| Арм | EX на 91 | EX без утечки (89) |
|---|---|---|
| zeroshot | 5.49% | 5.62% (5/89) |
| baseline | 23.08% | 22.47% (20/89) |
| **lora** (3 сида) | **27.84% ± 0.64** | **28.09% ± 1.12** |

Разрыв lora−baseline даже растёт (**+5.6 п.п.** без утечки): 2 контаминированных вопроса модель почти
всегда проваливает, а заученный ответ сработал лишь на одном сиде (q323, seed0) — то есть
результат не держится на утечке. Для будущих прогонов `build_dataset.py` теперь автоматически
выкидывает такие пары; вычищенный набор — `dataset/train_clean.json` (1171 → 1169).

**Ablation** (одиночные прогоны, если не сказано иное; читать с поправкой на шум ±2 п.п.):

| Вариант | EX | вывод |
|---|---|---|
| synth_50 / 143 / 347 / **1171** | 9.9 / 11.0 / 16.85 / **27.84%** | кривой рост до конца, плато нет (1171 — 3 сида) |
| synth_347 vs unfiltered_347 | 16.9\* vs 15.4% | фильтр +1.5 п.п. — **внутри σ, не доказан** |
| real_143 vs synth_143 | 13.2% vs 11.0% | живые чище, но разница в пределах шума |

\* synth_347 взят по среднему трёх сидов (16.85), а не по единственному прогону (17.58), с которого
раньше выводился «фильтр +2.2 п.п.». На сид-скорректированном среднем эффект фильтра падает до +1.5 п.п.
и не выходит за σ = 1.37; unfiltered гонялся один раз, повторов нет — честный вывод: **не доказан**.
Устойчив только эффект размера данных. Различия < 2–3 п.п. на 91 вопросе — шум одного прогона.

## Пайплайн

Всё, кроме обучения, гоняется локально. Обучение — на Kaggle (T4/P100, 4-bit).
База доступна только через ssh-туннель, поэтому Kaggle её не видит: туда уезжает готовый датасет,
оттуда — предсказания, EX считается дома.

```
профиль БД ──► генерация пар ──► фильтр исполнением ──► датасет ──► QLoRA (Kaggle) ──► предсказания ──► EX (дома)
collect_profile   generate_pairs      filter_pairs      build_dataset  kaggle_*.ipynb                  bird_evaluate_only
```

### 0. Подготовка

Туннель к базе (пароль у куратора; `ServerAliveInterval` чтобы не отваливался):

```bash
ssh -N -o ServerAliveInterval=60 -L 5444:10.11.1.6:5444 <user>@lnsigo.mipt.ru -p2278
```

`.env` в корне репозитория (в `.gitignore`, секреты не коммитить): `DB_USER`, `DB_PASS`,
`BENCHMARK_DB_URL=localhost:5444`, `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL_NAME`.

На Windows все запуски — с `PYTHONIOENCODING=utf-8`, иначе `print` падает на cp1251-консоли.

### 1. Профиль БД (локально, нужен туннель)

```bash
uv run --env-file .env python db2model/collect_profile.py
```

Складывает в `db2model/profiles/<db>.json` схему, FK, `pg_stats` и реальные значения.
Из профиля собирается M-Schema (носитель знания о БД для baseline и light-RAG):

```bash
uv run python db2model/build_mschema.py            # -> db2model/mschema/<db>.txt
```

Проверить достаточность профиля (teacher отвечает по нему на реальные вопросы, без доступа к БД):

```bash
uv run --env-file .env python db2model/validate_profile.py toxicology 6
```

### 2. Генерация и фильтр (локально, нужен туннель)

```bash
uv run --env-file .env python db2model/generate_pairs.py financial 200
uv run --env-file .env python db2model/filter_pairs.py financial
```

`generate_pairs` кормит профиль teacher-модели и просит N пар; `filter_pairs` выполняет каждый SQL
на живой базе, брак выкидывает в `db2model/clean/<db>.rejected.json` с причинами (доля брака ~30%).

### 3. Сборка датасета (локально)

```bash
uv run python db2model/build_dataset.py       # train/val + manifest
uv run python db2model/build_ablation.py       # варианты для ablation
```

Готовые файлы для заливки собираются в `db2model/kaggle_input/`.

### 4. Обучение (Kaggle)

Залить `db2model/kaggle_input/` как Kaggle Dataset, включить GPU + Internet, поправить `DATA_DIR`
в первой ячейке под путь своего датасета. Затем запустить один из ноутбуков:

- `kaggle_train_lora.ipynb` — основной замер (target 3B): baseline, lora, zeroshot в одном прогоне.
- `kaggle_train_7b.ipynb` — тот же замер на **плановом target 7B** (batch 1 + gradient checkpointing,
  тег адаптера `synth1171_7b`); даёт строку 7B в лидерборде.
- `kaggle_ablation.ipynb` — пять вариантов данных, по адаптеру на каждый.
- `kaggle_seeds.ipynb` — повтор главного замера на 3 сидах (±σ).

Забрать домой `query_results_*.json` (и адаптер, если нужен артефакт).

### 5. Оценка (локально, нужен туннель)

Каждый файл предсказаний сначала через извлечение SQL (снимает прозу вокруг блоков кода),
потом EX:

```bash
uv run python db2model/extract_sql.py query_results_lora.json
uv run --env-file .env python bird_evaluate_only.py query_results_lora_extracted.json data/bird_large.json
```

## Структура

```
db2model/
  collect_profile.py    профиль БД из PostgreSQL
  build_mschema.py      профиль -> M-Schema (mschema/<db>.txt), носитель знания о БД
  validate_profile.py   проверка достаточности профиля
  generate_pairs.py     teacher генерирует пары по профилю
  filter_pairs.py       фильтр по исполнению (noise correction)
  build_dataset.py      сборка train/val + manifest (с деконтаминацией против оценки)
  check_leakage.py      аудит утечки train→eval (точный gold-SQL твин)
  build_ablation.py     варианты датасета для ablation
  extract_sql.py        извлечение SQL из ответа модели перед оценкой
  kaggle_train_lora.ipynb   основной замер 3B (baseline vs lora vs zeroshot)
  kaggle_train_7b.ipynb     тот же замер на плановом target 7B
  kaggle_seeds.ipynb        повтор на 3 сидах (±σ)
  kaggle_ablation.ipynb     ablation (5 вариантов данных)
  profiles/  raw/  clean/  dataset/  results/   артефакты этапов
  kaggle_input/         то, что заливается на Kaggle
```

## Ограничения

- **Teacher = Qwen3.6-27B** (сильный open-teacher из пула МФТИ; ранние замеры — на Qwen-7B).
  Внешний GPT-класс под разметку не выдавали, поэтому не «сильный→слабый GPT-дистилл»,
  а перенос схемы в веса от сильной open-модели + noise correction фильтром исполнения.
  Апгрейд 7B→27B дал +5.5 п.п. (см. главный результат).
- **Per-DB против multi-DB.** Обучен один адаптер сразу на три базы. Обобщение на новую БД без
  дообучения — вне скоупа.
- **Шум прогонов и сиды.** Главный замер (train 1171) усреднён по **3 сидам** (0/1/2,
  `kaggle_seeds.ipynb`): EX 27.47/27.47/28.57 → 27.84% ± 0.64. baseline детерминирован (greedy).
  Разрыв lora−baseline (+4.8 п.п.) кратно больше σ. Ранее публиковавшийся одиночный seed 42 (29.67%)
  оказался выше среднего — иллюстрация, зачем нужны повторы. ablation-варианты (фильтр, real vs synth)
  всё ещё по одному сиду, их различия внутри шума.
- **Диалект.** Gold BIRD в SQLite приводится к PostgreSQL через sqlglot; редкие конструкции могут
  не транспилироваться.
